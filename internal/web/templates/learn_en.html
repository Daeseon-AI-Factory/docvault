Mindset, one line
You don't need to memorize the code line by line. If you can explain the big picture + the six "why I chose this" decisions in your own words, you're set. It was built with AI help, but I drove the architecture, the decisions, the verification, and the deployment — that's the point.

1. One-liner + the big picture

One-liner: "An insider-threat monitoring tool for small teams that collects, records, and reviews data-exfiltration activity on employee PCs (copy, USB, external transfer)."

What it is NOT (say this too): not DRM, not ML-based UEBA, not a legal-evidence system, not a finished production security product.

[Employee PC] [Server (cloud)] [Admin] agent (clipboard) ─┐ osquery (file/USB)─┼─PSK · HTTPS─▶ ingest → PostgreSQL │ └ DB trigger: hash chain (tamper-proof) │ └ rule engine: risk score → Slack alert └───────────────▶ web UI + AI assistant ◀── Admin
  1. Install a small agent (+ optional osquery) on the employee PC
  2. It ships activity to the server (authenticated with a PSK)
  3. The server stores it in Postgres; a trigger builds a hash chain to detect tampering
  4. A rule engine scores risky behavior → alerts
  5. The admin reviews via the web UI / AI assistant (actions are reversible)

2. The stack — why / alternatives / trade-offs

The classic interview question is "why did you use X?" → just give each card's trade-off.

① Language: Go

whatGoogle's language; compiles to a single dependency-free executable.

whyDeploy is one file (server + agent), great concurrency, fast and lightweight, crypto in the standard library.

alternativesPython (slow, heavy to deploy) · Node (needs a runtime) · Java (heavy, verbose).

trade-offSimple and easy to ship (+) ↔ code can be a bit repetitive (−). For a small team running one language across server and agent, Go is the sweet spot.

② Database: PostgreSQL

whatThe most trusted open-source relational database.

whyTop-tier integrity, triggers to automate the hash chain, JSON support, free.

alternativesMySQL (slightly fewer features) · SQLite (light but weak concurrent writes) · MongoDB (flexible schema but weaker integrity/joins).

trade-offStrong integrity and features (+) ↔ heavier to operate than SQLite (−). For a product where audit and integrity are the point, Postgres is the right call.

③ Router: chi

whatA lightweight Go library that routes requests to the right handler.

why100% compatible with the standard net/http and keeps middleware (audit, auth) clean.

alternativesRaw net/http (more manual) · gin/echo (more features, heavier, opinionated).

trade-offClose to the standard, easy, low lock-in (+) ↔ fancy features you wire yourself (−).

④ DB access: pgx + sqlc (no ORM)

whatA Postgres driver plus a tool that turns SQL into type-safe Go code.

whyDirect control over SQL + type safety, and parameterized queries shut down SQL injection.

alternativesAn ORM (GORM): convenient but slower, weak on complex queries, lots of "magic".

trade-offControl, performance, transparency (+) ↔ a bit more typing (−). When correct queries matter (security/audit), raw SQL beats ORM magic.

⑤ Auth: JWT (instead of server sessions)

whatA signed token (a tamper-proof badge) stored in a cookie.

whyThe server doesn't hit a session store on every request (scales); the token carries identity and role.

alternativesServer-side sessions: easy instant revocation, but you need a store.

trade-offLight and scalable (+) ↔ revoking a token before it expires is awkward (−) → mitigated with short expiry + refresh.

⑥ UI: htmx + Go templates (instead of React)

whatThe server sends HTML fragments and htmx swaps just that piece in. No JS build step.

whyBuild a dynamic UI fast, with no heavy front-end toolchain, in one language (Go).

alternativesReact/Vue (SPA): app-like UX, but build, complexity, and front-end staffing.

trade-offSimple, fast to build (+) ↔ limits for highly interactive screens (−). For an internal admin tool, htmx is the best bang for the buck.

⑦ Encryption: AES-256-GCM (chunked)

whatFiles are split into 64 KB chunks, each encrypted with AES-256-GCM.

whyGCM gives confidentiality and tamper detection together. Chunking streams large files and detects reordering/truncation.

alternatives (dropped)AES-CTR: fast but no tamper detection → we caught the risk and switched to GCM (a real incident).

trade-offSafe, integrity included (+) ↔ slightly heavier (−). For a security product, GCM every time.

⑧ Key management: envelope encryption

whatEach file is encrypted with its own key; that file key is encrypted with the master key and stored in the DB.

whyYou only have to protect one master key. Key rotation and isolation become easy.

alternativesEncrypt every file directly with the master key: simple, but rotating means re-encrypting everything, and no isolation.

trade-offOperational flexibility (+) ↔ one extra layer of structure (−). The standard answer when you have many files and key rotation.

⑨ Log integrity: DB-trigger hash chain

whatOn insert, a trigger automatically computes a hash of "previous row's hash + this content" and chains them.

whyIf someone edits or deletes a log directly in the DB, the chain breaks and it's detectable.

alternativesPlain append-only log (weak tamper detection) · external immutable store (powerful but complex/costly).

trade-offLow cost, good detection (+) ↔ you must handle concurrent-insert races (−) → solved with an advisory lock.

⑩ Collection: osquery + our own clipboard agent

whatFile/USB/process via osquery (existing open source); clipboard via a small agent we wrote.

whyDon't reinvent the wheel — use battle-tested osquery, and only build the clipboard piece it can't see.

alternativesBuild everything ourselves (more time/bugs) · a commercial EDR (expensive/overkill).

trade-offBalances cost and reliability (+) ↔ you must merge two systems for the user (−) → solved with a "unified timeline".

⑪ Agent execution: a Windows Scheduled Task (not a service)

whatA per-user task that auto-runs the agent in the interactive session at logon.

whyA Windows service runs in Session 0 (no desktop) and can't read the clipboard. A scheduled task runs in the user's session → capture works (a real fix we made).

alternativesA service (can't capture) · manual run (stops when closed).

trade-offCaptures + auto-starts (+) ↔ less isolation/management tooling than a service (−). If the clipboard is the goal, a scheduled task is the right answer.

⑫ AI: tool-use (instead of RAG)

whatGive the model tools (query / create / assign) and let natural-language requests trigger those tool calls (OpenAI/Gemini).

whyThe data is structured (DB), so SQL tools fit better than document search (RAG) → answers are grounded in real rows (less hallucination). Mutations require human confirmation + are reversible.

alternativesRAG (great for document Q&A, wrong for structured data) · fine-tuning (expensive/overkill).

trade-offAccurate, real-time, can act (+) ↔ needs tool/permission design and injection defense (−) → solved with a confirmation gate.

⑬ Deployment: Docker Compose + shared box + Caddy

whatServer and DB as containers, co-located on one cloud box with another project, with Caddy handling automatic HTTPS.

whyCuts cost (share a box) + simple deploy + automatic certificates.

alternativesInstall per server (poor reproducibility) · Kubernetes (powerful but overkill for one person) · Nginx (manual certs).

trade-offSimple and cheap (+) ↔ limits for high availability / large scale (−). The right answer for solo ops; revisit k8s when it grows.

3. Glossary (from zero)

Basic structure (server, backend, etc.)

Server: an always-on computer that handles requests (the kitchen). Client: the requester (a browser).

Backend: the logic/server/data behind the scenes. Frontend: the screen the user sees.

Compile: translate human code into something the computer runs → a binary (executable, .exe).

Middleware: a step that runs before/after every request (e.g. "check login", audit logging).

Database

DB: a data warehouse. Table: a sheet like Excel. Row/column: one record / a field.

SQL: the language to talk to the DB. Query: one such question. Transaction: group steps as "all or nothing".

Trigger: an automatic action inside the DB when something happens. Migration: applying DB-structure changes in order.

Web communication

HTTP: the browser↔server conversation rules. HTTPS: the encrypted version (the padlock).

API: a defined window for programs to talk. Endpoint: one concrete API address (e.g. /api/events/clipboard).

Routing: directing each incoming request to the right handler.

Security (the core)

Encryption: scramble so it's unreadable without a key. Key: the secret that locks/unlocks. AES-256: the standard symmetric cipher. GCM: a mode that does encryption + tamper detection.

Hash: a fixed-length "fingerprint" of data (not reversible). Hash chain: link each row's fingerprint to the previous to detect tampering.

Authentication: who are you (login). Authorization: are you allowed. JWT: a tamper-proof badge token. 2FA/TOTP: password + a 6-digit code.

CSRF: another site abusing your logged-in state → blocked with a CSRF token. Rate limit: cap the number of attempts (stops brute force).

PSK: a pre-shared secret between server and agent. fail-closed: if config is missing, deny rather than allow. Code signing: a "verified publisher" stamp on the executable (without it, Windows shows a SmartScreen warning).

Endpoint (employee PC) · AI · deployment

Agent: the small monitoring program on the PC. Scheduled Task: auto-runs at logon in the user session (so the clipboard can be captured). osquery: open source that queries the PC like SQL.

LLM: a language AI like ChatGPT. Tool-use: the AI calls defined functions. RAG: find documents then answer. Hallucination: the AI making things up. Prompt injection: hiding commands in data to trick the AI.

Container/Docker: a standard box holding the program + its environment. Reverse proxy: a front desk that routes requests to back services (Caddy). CI: a robot that auto-builds/tests on every push. Commit/branch/PR/merge: units of code-history management.

4. Six core concepts (analogy + interview answer)

① Envelope encryption

Analogy: lock valuables in small safes (file keys), and keep those keys in one bigger master safe.

"Each file is encrypted with its own AES-256-GCM key, and those keys are sealed with a master key in the DB — which makes key rotation and isolation easy."
② Hash chain

Analogy: a ledger where each page records the previous page's fingerprint — tear one out and it shows.

"I guarantee audit-log integrity with a DB-trigger hash chain, and I serialize concurrent inserts with a transaction-scoped advisory lock."
③ Agent + PSK

Analogy: no badge (PSK), no entry. The clipboard is only visible from the employee's own desk (their session).

"The agent authenticates with a PSK header, and the server is fail-closed if no PSK is configured. The clipboard is session-bound, so I run the agent as a scheduled task in the user's session."
④ AI tool-use

Analogy: hand the AI a fixed set of buttons (tools); the dangerous buttons only fire after a human confirms.

"Since the data is structured, I went with tool-use instead of RAG. Read tools run immediately; mutating tools require an explicit confirmation turn, and every change is audited and reversible."
⑤ Auth & access control

Analogy: the badge (JWT) states your rank; the admin door only opens after checking it. 2FA is an extra lock.

"I enforce access control at both the route and the repository boundary, and I store 2FA secrets encrypted with the master key rather than in plaintext."
⑥ Deployment (Docker/Caddy)

Analogy: pack everything into a standard shipping container so it unpacks the same anywhere. Caddy is the building's front desk.

"I deploy with Docker on a single cloud box and get automatic TLS from Caddy. The demo runs as a separate stack, isolated from real data."

5. Likely interview questions

Q. One-line description? / Why did you build it?
The one-liner + "small teams want to catch internal data leaks without an expensive security suite."
Q. Hardest technical problem?
(pick one) the hash-chain concurrency race (solved with an advisory lock) / the clipboard not being readable from Session 0 (switched to a scheduled task) / unsigned-.bat install friction (SmartScreen).
Q. How is it secured?
Envelope encryption + hash chain + roles/2FA + fail-closed agent PSK + parameterized SQL.
Q. AI wrote much of the code — what's your contribution?
"I drove the architecture, the technical decisions, the adversarial review, and the deployment. For example, an adversarial review caught a passwordless-admin vulnerability in the demo login, which I then fixed."
Q. What would you change to scale it?
Code signing, multi-tenancy, high availability, a proper osquery end-to-end verification, and real (ML) UEBA.

6. Honest weaknesses (saying them first scores points)

• Much of the code was AI-written → frame it as "I drove the architecture, decisions, verification, and deployment."
• Single box (not highly available), osquery e2e unverified, small-scale target, unsigned agent (SmartScreen).
• Be explicit that it's not a production security product — not overstating it builds trust.
