# Decisions

주요 설계 결정과 트레이드오프. 각 결정마다 다른 길을 택했을 때 무엇이 달라지는지 명시한다.

---

## ADR-001 — 언어로 Go를 선택

**결정**: 서버와 클립보드 에이전트 모두 Go로 작성.

**주요 동기는 에이전트 배포다.** 클립보드 에이전트는 사용자 PC(Windows + macOS) 양쪽에 배포된다. Java면 사용자 PC마다 JVM이 깔려야 하고, Python이면 PyInstaller로 50MB+ 바이너리에 DLL 패키징 지옥. Go는 `GOOS=windows GOARCH=amd64`로 9MB 정적 바이너리 한 개가 나온다.

서버를 같은 언어로 통일한 부수 이유:

- 동시성 모델이 워크로드에 맞는다. osquery 배치 POST + 클립보드 에이전트 실시간 + 웹 요청 + SSE 스트림이 goroutine 모델로 자연스럽다.
- 정적 타입 + 컴파일 시간 검증이 보안 소프트웨어에 적절하다. Python + mypy는 ~70%, Go는 기본 100%.
- 보안 도구 생태계가 Go 친화적이다. Velociraptor, Falco, Trivy, k8s security 도구 다수가 Go.

**트레이드오프**:

- 제네릭이 1.18 이후에야 들어왔고 여전히 제한적이라 일부 추상화가 코드 중복으로 남는다.
- ML/데이터 분석은 Go가 약하다. 현재 UEBA(룰 기반)는 Go로 충분하지만, 모델 기반으로 확장한다면 Python 마이크로서비스 분리가 정답이다.
- Java/Spring 생태계의 SI 인력 풀이 더 크다. 한국 엔터프라이즈 인수인계 시 불리.

**대안 평가**:

- **Kotlin/Spring**: 에이전트 배포 문제(JVM 강요)가 해결 안 됨. 서버만 Kotlin으로 가도 에이전트는 어차피 다른 언어 필요.
- **Rust**: 메모리 안전성은 추가 이득이지만 개발 속도 대가가 크다. 1인 단기 프로젝트엔 부적합.
- **Python**: 출시 속도는 빠르지만 에이전트 배포 문제 동일하고, 보안 SW 신뢰성 측면에서 정적 타입 부재가 부담.

## ADR-002 — PostgreSQL 단독, Kafka·Redis·Elasticsearch 미사용

**결정**: 모든 데이터를 PostgreSQL 한 곳에. 메시지 큐, 캐시, 검색 엔진을 별도로 도입하지 않는다.

**근거**:

- 의도된 규모는 ~40 사용자, ~50K 이벤트/일, ~100 엔드포인트. 이 규모에서 PostgreSQL이 모든 워크로드를 감당한다.
- Full-text 검색은 PostgreSQL `tsvector`로 충분. 별도 Elasticsearch 클러스터는 운영 복잡도만 늘림.
- 큐가 없어 백프레셔 처리는 필요하지만, 인라인 처리(이벤트 → INSERT → 트리거 → 분석기 호출) 가 단순하다. 실패해도 HTTP 응답이 5xx로 떨어지면 에이전트가 재전송한다.

**확장 임계점**:

- 100K 이벤트/일 초과 시: 인덱스 압박. 파티셔닝 검토.
- 다중 소비자 필요 시(예: 별도 분석 파이프라인): NATS 도입 검토. Kafka는 여전히 오버킬.
- 검색 성능 부족 시: pg_trgm 인덱스 우선, 그래도 부족하면 외부 검색 엔진.

**트레이드오프**: 단일 PostgreSQL이 SPOF. 백업과 복구가 운영의 전부다. HA가 필요한 환경엔 부적합.

## ADR-003 — 차단(Prevention)이 아니라 탐지(Detection)

**결정**: osquery 기반 user-mode 탐지만 한다. 커널 드라이버, DLL 인젝션, OS 후킹 없음.

**근거**:

- 커널 모드 작업은 CAD 같은 엔지니어링 워크플로를 깨는 빈도가 높다. Fasoo·Softcamp 도입한 한국 제조업에서 흔한 불만.
- 1인 OSS는 커널 드라이버 코드 사인·인증·QA 비용을 감당할 수 없다.
- 글로벌 시장에 IRM(Insider Risk Management) 카테고리가 인정된다. Code42, Cyberhaven 등이 같은 포지션.

**트레이드오프**:

- **차단 못 한다.** 사용자가 USB로 파일 복사하면 사후에 알게 된다.
- 따라서 이 도구는 *DRM의 대안*이 아니라 *다른 카테고리*다. DRM이 필요한 곳에는 부적합.
- CISO 입장에서 "사고 시 책임 분산"이라는 DRM의 정치적 가치를 제공하지 못한다.

**의도된 사용처**: DRM 비용을 못 감당하거나 워크플로 영향 때문에 도입을 거부한 소규모 팀. 차단보다 사후 조사·증거 보존이 우선인 환경.

## ADR-004 — htmx + Go 템플릿, React 미사용

**결정**: 서버 렌더링 HTML + 부분 갱신만 htmx로 처리. SPA 프레임워크 사용 안 함.

**근거**:

- 빌드 스텝 0. `node_modules` 없음. 의존성 트리 얕음.
- 페이지가 ~15개 수준의 어드민 도구라 SPA 라우팅·상태 관리·코드 스플리팅이 불필요.
- 서버 렌더 = 검색엔진과 무관, JS 비활성 환경에서도 기본 동작.

**트레이드오프**:

- 클라이언트 상호작용이 복잡해지면 부담. 현재 SSE 대시보드 정도는 잘 작동.
- 디자이너·프론트 인력 협업 시 학습 곡선이 React보다 가파를 수 있음.

**임계점**: 페이지가 100개를 넘거나 클라이언트 사이드 상태 관리(드래그앤드롭 트리, 복잡한 폼 등)가 필요해지면 React 검토.

## ADR-005 — 단일 서버 on-premise 설계

**결정**: 모든 서비스(HTTP, DB, 파일 저장소)가 한 호스트에 박힌다. 클라우드 매니지드 서비스를 가정하지 않는다.

**근거**:

- 의도된 사용자가 자체 인프라에 배포하는 소규모 팀이다. 데이터 주권이 중요한 환경(KISA, GDPR 등)에 적합.
- 단일 서버 운영 비용이 클라우드 매니지드보다 낮다(40 사용자 기준).
- 배포 토폴로지가 단순해 운영자가 전체를 한 사람의 머릿속에 담을 수 있다.

**트레이드오프**:

- HA 없음. 서버 다운 = 서비스 전체 중단.
- 수평 확장 불가. 100 사용자 정도까지가 한계로 추정.
- 디스크 단일 장애가 vault 손실로 직결. 백업이 운영의 전부.

**클라우드 배포 가능 여부**: 가능. AWS EC2 1대에 같은 토폴로지를 그대로 박을 수 있다. 자세한 사항은 [DEPLOYMENT.md](DEPLOYMENT.md).

## ADR-006 — 감사 로그를 DB 트리거 기반 해시 체인으로

**결정**: `audit_logs`와 `endpoint_events` 테이블에 `prev_hash`/`row_hash` 컬럼을 추가하고, INSERT 트리거가 SHA256으로 체인을 계산한다. UPDATE/DELETE는 트리거로 차단한다.

**근거**:

- 어플리케이션 코드 레벨에서 강제하면 우회 위험(개발자가 코드 우회, 다른 클라이언트가 직접 DB 접근).
- DB 트리거는 어떤 클라이언트든 INSERT만 들어오면 자동 적용된다.
- pgcrypto의 `digest()` 함수로 PL/pgSQL 안에서 SHA256 계산이 가능하다.

**트레이드오프**:

- DB superuser는 트리거 비활성화 후 행 수정·재계산이 가능하다. *진짜* 변조 불가능을 원하면 RFC 3161 외부 timestamping 또는 append-only WORM 스토리지 필요.
- 현재 트리거의 `SELECT ... ORDER BY id DESC LIMIT 1`은 직렬화가 없어 동시 INSERT 시 같은 prev_hash를 두 행이 가질 수 있다(체인 분기). 운영 환경에선 advisory lock 또는 SERIALIZABLE 트랜잭션 필요.

**알고 있는 한계는 [LIMITATIONS.md](LIMITATIONS.md)에 상세 기술.**

## ADR-007 — UEBA가 아니라 룰 기반 점수화

**결정**: 사용자 행위 이상 탐지를 머신러닝이 아닌 임계값 기반 룰 10종으로 구현한다. 사용자 베이스라인은 SQL 집계로 30일 평균을 매일 재계산한다.

**근거**:

- 1인 단기 프로젝트에서 모델 학습·평가·재학습 파이프라인을 갖추는 비용이 과도하다.
- 의도된 규모(40 사용자)에선 룰 10종으로도 의미 있는 탐지가 가능하다.
- 룰은 설명 가능(`야간 접근: 21:30 활동, 평소 08:00–19:00`)해서 분쟁 시 근거 제시가 쉽다.

**용어**: 이 시스템을 *UEBA*라고 부르는 것은 부정확하다. 업계에서 UEBA는 일반적으로 ML 기반 anomaly detection을 의미한다. 정직한 이름은 *rule-based anomaly scoring*이다. 코드의 `internal/ueba/` 디렉토리명은 역사적 잔재이며 이름 변경 후보다.

**확장 경로**: 모델 기반으로 가야 한다면 Python 마이크로서비스로 분리. Go 서버는 이벤트를 그대로 전달하고 점수만 받아오면 된다.

## ADR-008 — 파일 본체 암호화에 chunked AES-256-GCM 사용

**결정**: 파일 본체를 chunked AES-256-GCM으로 스트리밍 암호화한다. 파일 키 자체는 AES-256-GCM으로 마스터 키에 봉인한다(envelope encryption).

**이력**: 초기 구현은 AES-256-CTR이었으나 MAC이 없어 무결성 보장이 안 되는 결함이 있어 2026-05 chunked GCM으로 교체.

**포맷**:

- 평문을 64 KiB 청크 단위로 분할
- 각 청크는 GCM으로 독립 암호화 (16 바이트 인증 태그 부착)
- 청크별 nonce: `file_nonce[0:8] || chunk_index (3 bytes BE) || final_flag (1 byte)`
- `final_flag`는 마지막 청크에서만 `0x01` — truncation 공격 방지
- `chunk_index`는 청크마다 1씩 증가 — reorder 공격 방지
- 디스크 포맷: ciphertext 청크의 단순 연결 (base nonce는 DB에 별도 저장)

**검증된 공격 시나리오** (`encryption_test.go`):

- 청크 본문 비트 플립 → 복호화 실패
- GCM 인증 태그 비트 플립 → 복호화 실패
- 마지막 청크 제거 (truncation) → 복호화 실패 (직전 청크가 final_flag 불일치로 인증 실패)
- 청크 순서 바꿈 (reorder) → 복호화 실패 (chunk_index 불일치로 nonce 변경)
- 잘못된 키 / 잘못된 nonce → 복호화 실패

**트레이드오프**:

- GCM이 CTR보다 약간 느림. 다만 AES-NI 지원 CPU(현대 x86/ARM)에서는 거의 동등.
- 청크당 16바이트 인증 태그 오버헤드 (64 KiB 청크 기준 0.024%).
- 청크 인덱스가 3바이트(24비트)라 최대 16M 청크 = 1 TiB 파일 한계. 그 이상은 명시적 에러.

**옵션 B (CTR + 별도 HMAC) 검토 결과**: 청크 단위 무결성 검증 불가(전체 파일을 한 번 읽어야 함). 부분 손상 위치 특정도 불가. 채택 안 함.

## ADR-009 — 에이전트 인증에 PSK 사용 (개선 여지)

**결정**: osquery와 클립보드 에이전트는 pre-shared key(`DOCVAULT_OSQUERY_PSK`)로 서버에 인증한다.

**원래 근거**: 초기 구현 단순화. 40개 엔드포인트 규모면 키 분배가 어렵지 않다.

**한계**:

- PSK 노출 시 모든 에이전트가 영향. 키 회전이 무겁다.
- 에이전트 개별 식별·취소·감사가 PSK 단독으론 불가능.

**개선 방향** (미구현): 에이전트별 mTLS 인증서. 등록 시 서버가 발급, 취소는 CRL 또는 단순한 revocation 테이블. osquery는 기본적으로 mTLS를 지원하므로 osquery 쪽 통합은 자연스럽다.

## 변경 이력

- 2026-05: 초기 작성. ADR-001 ~ ADR-009. 일부 ADR(006, 008, 009)에 알려진 한계를 명시.
- 2026-05: ADR-008 갱신. 파일 본체 암호화를 AES-CTR → chunked AES-GCM으로 교체. truncation·reorder·tamper 방어 추가. 마이그레이션 013에서 해시 체인 트리거에 advisory lock 추가하여 ADR-006의 동시성 race 해결.
