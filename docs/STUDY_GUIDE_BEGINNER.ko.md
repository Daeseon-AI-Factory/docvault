# A. 기초 용어 사전 (이것만 알면 80%)

## A-1. 프로그램이 도는 기본 구조
- **프로그램 / 코드**: 컴퓨터한테 시키는 명령문 모음.
- **프로그래밍 언어**: 그 명령을 쓰는 언어. 사람마다 한국어/영어 쓰듯, 컴퓨터용 언어도 여러 개(Go, Python, 자바스크립트...).
- **컴파일(compile)**: 사람이 쓴 코드를 컴퓨터가 바로 실행하는 형태로 "번역"하는 것. → 결과물이 **바이너리(실행파일)** (윈도우의 `.exe` 같은 거).
- **런타임(runtime)**: 프로그램이 실제로 돌아가고 있는 동안/환경.
- **서버(server)**: 24시간 켜져서 요청을 받아 처리하는 컴퓨터(또는 그 프로그램). 식당의 주방.
- **클라이언트(client)**: 서버한테 요청하는 쪽. 손님(브라우저, 앱).
- **백엔드(backend)**: 눈에 안 보이는 뒤쪽 — 서버, 데이터 처리, 로직. (주방)
- **프론트엔드(frontend)**: 사용자가 보는 화면. (손님 테이블/메뉴판)

## A-2. 데이터베이스 (DB)
- **데이터베이스(database)**: 데이터를 체계적으로 저장하는 창고.
- **테이블(table)**: 엑셀 시트처럼 생긴 표. (예: `users` 표, `events` 표)
- **행(row)/열(column)**: 표의 가로 한 줄(데이터 하나) / 세로 항목(이름, 이메일...).
- **SQL**: 데이터베이스한테 말 거는 언어 ("이 조건인 행 다 보여줘").
- **쿼리(query)**: SQL로 던지는 질문/명령 한 번.
- **트랜잭션(transaction)**: 여러 작업을 "다 되거나 다 안 되거나"로 묶는 것. 은행 이체(빼기+넣기)가 중간에 끊기면 안 되는 것처럼.
- **트리거(trigger)**: 어떤 일이 생기면 자동으로 따라 실행되는 DB 안의 작은 자동장치. (예: 새 로그가 들어오면 자동으로 해시 계산) ← 우리가 변조 방지에 씀.
- **마이그레이션(migration)**: DB 구조(표 모양)를 바꾸는 변경을 순서대로 기록·적용하는 것. (001, 002... 번호 매김)

## A-3. 웹 통신
- **HTTP**: 브라우저↔서버가 대화하는 규칙. **HTTPS**는 그걸 암호화한 안전 버전(주소창 자물쇠).
- **요청(request)/응답(response)**: 손님이 주문(요청) → 주방이 음식(응답).
- **API**: 프로그램끼리 주고받는 "창구/규격". (직원이 아니라 정해진 창구로만 주문)
- **엔드포인트(endpoint)**: API의 구체적 주소 하나. (예: `/api/events/clipboard` = "클립보드 이벤트 받는 창구")
- **라우터/라우팅(router/routing)**: 들어온 요청을 "이 주소는 이 처리로" 보내주는 교통정리.
- **미들웨어(middleware)**: 요청이 처리되기 전후에 공통으로 끼어드는 단계. (예: "로그인했나 검사" → 모든 요청에 자동 적용) ← 우리 감사 로그/인증이 이걸로 동작.

## A-4. 보안 (이 제품의 핵심)
- **암호화(encryption)**: 내용을 열쇠 없이는 못 읽게 뒤섞는 것. **평문**(원본) ↔ **암호문**(뒤섞인 것).
- **키(key)**: 암호를 잠그고 푸는 열쇠(긴 비밀 숫자).
- **대칭키 암호 / AES**: 같은 열쇠로 잠그고 푸는 방식. **AES-256**은 그 표준(매우 안전, 은행·정부도 씀).
- **GCM**: AES를 쓸 때 "내용이 중간에 변조됐는지"까지 같이 확인해주는 모드. (그냥 암호화 = 내용 숨김만; GCM = 숨김 + 위조 탐지)
- **해시(hash)**: 어떤 데이터든 고정 길이의 "지문"으로 바꾸는 것. 내용 1글자만 바뀌어도 지문이 완전 달라짐. 되돌리기는 불가.
- **해시체인(hash chain)**: 로그 줄마다 "앞 줄 지문 + 내 내용"의 지문을 적어 사슬로 엮음 → 한 줄만 고쳐도 사슬이 끊겨 들킴. (블록체인의 핵심 원리와 같음)
- **인증(authentication)**: "너 누구냐"를 확인(로그인).
- **인가/권한(authorization)**: "너 이거 해도 되냐"를 확인(관리자만 가능 등).
- **세션(session)/쿠키(cookie)**: 로그인 상태를 유지하는 방법. 쿠키 = 브라우저가 들고 다니는 작은 출입증.
- **JWT(제이슨 웹 토큰)**: 서명된 출입증. 안에 "나는 admin 유저 3번"이 적혀 있고 위조 못 하게 서명됨. 서버가 매번 DB 안 봐도 신원 확인 가능.
- **토큰(token)**: 신원/권한을 담은 출입증 문자열(JWT가 그 일종).
- **2FA / TOTP**: 비밀번호 + 추가 1단계(앱의 6자리 숫자). TOTP = 그 6자리를 만드는 표준.
- **CSRF**: 다른 사이트가 네 로그인 상태를 악용해 몰래 요청 보내는 공격. **CSRF 토큰**으로 막음.
- **레이트리밋(rate limit)**: "1분에 N번까지만" 제한. 비밀번호 무차별 대입 공격 차단.
- **PSK(사전 공유 키, pre-shared key)**: 서버와 에이전트가 미리 나눠 가진 비밀 암호. 이게 맞아야 이벤트를 받아줌(아무나 가짜 못 보냄).
- **fail-closed**: 뭔가 설정이 빠지면 "열어두기"가 아니라 "막아버리기"로 안전하게 실패. (PSK 없으면 그냥 거부)
- **코드사이닝(code signing)**: 실행파일에 "이거 검증된 내가 만든 거다" 디지털 도장. 없으면 윈도우가 경고(SmartScreen)를 띄움.

## A-5. 엔드포인트(직원 PC) 쪽
- **에이전트(agent)**: 직원 PC에 깔리는 작은 감시 프로그램(우리가 만든 `dvclip.exe`).
- **서비스/데몬(service/daemon)**: 사용자가 안 켜도 백그라운드에서 계속 도는 프로그램.
- **예약 작업(Scheduled Task)**: 윈도우가 "로그인하면 이거 실행해" 식으로 자동 실행해주는 기능. ← 클립보드를 잡으려면 사용자 화면 세션에서 돌아야 해서 이걸 씀.
- **세션 0 문제**: 윈도우 "서비스"는 사용자 화면이 없는 세션(세션0)에서 돌아 **클립보드를 못 읽음**. 그래서 예약작업(사용자 세션)으로 바꿈.
- **osquery**: 회사가 만든 게 아니라 **이미 있는 오픈소스 도구**. PC의 파일/USB/프로세스를 SQL처럼 조회. 우리는 갖다 쓰기만(설정만).
- **클립보드(clipboard)**: 복사/붙여넣기 임시 저장소. 여기 감시 = 문서 복사 유출 탐지.

## A-6. AI 쪽
- **LLM(대규모 언어모델)**: ChatGPT 같은 "말 알아듣고 답하는" AI 모델(우리는 OpenAI/Gemini 사용).
- **프롬프트(prompt)**: AI한테 주는 지시문/질문.
- **할루시네이션(hallucination)**: AI가 모르면서 그럴듯하게 지어내는 것. ← 우리가 막아야 하는 것.
- **function calling / tool-use(툴 사용)**: AI한테 "이런 기능들(툴)을 쓸 수 있어"라고 주고, AI가 필요할 때 그 툴(예: DB 조회, 사용자 생성)을 호출하게 하는 것. → 답이 실제 데이터에 근거함.
- **RAG**: AI가 답하기 전에 "문서 더미에서 관련 문서를 찾아 읽고" 답하는 방식. 문서 Q&A에 적합.
- **프롬프트 인젝션(prompt injection)**: 공격자가 데이터(파일명 등)에 몰래 "관리자 계정 다 지워" 같은 명령을 숨겨 AI를 속이는 공격. ← 우리가 "변경은 사람 확인 후"로 막음.

## A-7. 배포·운영
- **컨테이너(container) / Docker**: 프로그램 + 필요한 모든 환경을 통째로 담은 "표준 상자". 어느 컴퓨터든 똑같이 실행됨. ("내 컴퓨터선 됐는데요" 문제 해결.)
- **이미지(image)**: 그 상자의 설계도/스냅샷. 이미지로 컨테이너를 찍어냄.
- **Docker Compose**: 여러 컨테이너(서버+DB 등)를 한 파일로 묶어 한 번에 띄우는 도구.
- **리버스 프록시(reverse proxy)**: 바깥 요청을 받아 뒤의 여러 서비스로 나눠 보내는 "안내데스크". 우리 건 **Caddy**.
- **TLS / 인증서(certificate)**: HTTPS(자물쇠)를 가능하게 하는 신원 증명. Caddy가 자동으로 발급/갱신.
- **깃(Git)**: 코드 변경 이력 관리(되돌리기·협업). **커밋**=저장점, **브랜치**=작업 갈래, **PR**=합치자는 요청, **머지**=합치기.
- **CI(지속적 통합)**: 코드 올릴 때마다 자동으로 빌드·테스트 돌려 "안 깨졌나" 확인하는 로봇(GitHub Actions).
- **임베드(//go:embed)**: 템플릿·이미지 같은 파일을 실행파일 안에 통째로 넣는 것 → 배포가 파일 하나로 끝.
- **SSR(서버사이드 렌더링)**: 화면 HTML을 서버가 미리 만들어 보내는 방식(브라우저에서 조립하는 SPA의 반대).

# B. 우리가 쓴 기술 하나하나 (뭐냐 / 왜 / 대안 / 트레이드오프)

> 면접에서 "왜 X 썼어요?"는 거의 무조건 나옵니다. 각 항목의 **트레이드오프**(이걸 얻는 대신 저걸 포기)를 말할 수 있으면 끝.

## B-1. 언어: Go
- **뭐냐**: 구글이 만든 프로그래밍 언어. 컴파일하면 의존성 없는 **단일 실행파일** 하나가 나옴.
- **왜**: ① 배포가 파일 하나로 끝(서버·에이전트 둘 다) ② 동시에 많은 요청 처리 잘함 ③ 빠르고 메모리 적게 씀 ④ 표준 라이브러리가 튼튼(암호화 등 기본 제공).
- **대안**: Python(쉽지만 느리고 배포 무거움), Node.js(자바스크립트, 생태계 크지만 런타임 필요), Java(강력하지만 무겁고 장황).
- **트레이드오프**: Go는 문법이 단순해 빨리 짜고 배포 쉬움(장점). 대신 일부 고수준 추상화·제네릭이 늦게 들어와 코드가 다소 반복적(단점). **소규모 팀 + 에이전트까지 한 언어로 = Go가 딱.**

## B-2. 데이터베이스: PostgreSQL
- **뭐냐**: 가장 신뢰받는 오픈소스 관계형 DB.
- **왜**: ① 데이터 정확성·신뢰성 최고 ② **트리거** 지원(해시체인 자동화) ③ JSON도 다룸 ④ 공짜·표준.
- **대안**: MySQL(비슷, 기능 약간 덜), SQLite(파일 하나 DB, 가볍지만 동시쓰기 약함), MongoDB(문서형, 스키마 자유롭지만 정합성·조인 약함).
- **트레이드오프**: PostgreSQL은 기능·정합성이 강함(장점). 대신 SQLite보다 운영(설치·관리)이 무거움(단점). **감사/무결성이 핵심인 보안 제품엔 정합성 강한 Postgres가 정답.**

## B-3. 웹 라우터: chi
- **뭐냐**: Go용 가벼운 라우팅 라이브러리(요청을 알맞은 처리로 보냄).
- **왜**: 표준 `net/http`와 100% 호환 + 미들웨어(감사/인증) 깔끔. 가볍고 군더더기 없음.
- **대안**: 순수 `net/http`(더 수동), gin/echo(더 많은 기능, 더 무겁고 자체 방식 강요).
- **트레이드오프**: chi는 표준에 가까워 배우기 쉽고 잠금(lock-in) 적음(장점). 대신 gin류의 화려한 기능은 직접 붙여야(단점). **단순·표준 선호 → chi.**

## B-4. DB 접근: pgx + sqlc (ORM 안 씀)
- **뭐냐**: pgx = Postgres 드라이버, sqlc = SQL을 타입 안전한 Go 코드로 생성.
- **왜**: SQL을 직접 쓰되(통제력·성능) 타입 안전(실수 줄임). **파라미터라이즈드 쿼리**로 SQL 인젝션 차단.
- **대안**: ORM(GORM 등) — 객체로 DB 다룸, 편하지만 느려지고 복잡 쿼리에 약하고 "마법" 많음.
- **트레이드오프**: 생SQL은 통제·성능·투명성(장점), 대신 타이핑이 좀 더 많음(단점). **보안/감사처럼 정확한 쿼리가 중요하면 ORM의 마법보다 생SQL.**

## B-5. 인증: JWT (서버 세션 대신)
- **뭐냐**: 서명된 출입증 토큰을 쿠키에 담음.
- **왜**: 서버가 매 요청마다 세션 저장소를 조회 안 해도 됨(확장성). 토큰 자체에 신원·권한 포함.
- **대안**: 서버사이드 세션(서버가 세션 목록을 메모리/DB에 보관) — 즉시 무효화 쉬움, 대신 저장소 필요.
- **트레이드오프**: JWT는 가볍고 확장 쉬움(장점). 대신 발급된 토큰을 만료 전 강제 취소가 까다로움(단점) → 우리는 짧은 만료 + 리프레시로 완화.

## B-6. 화면: htmx + Go 템플릿 (React 같은 SPA 대신)
- **뭐냐**: 서버가 HTML 조각을 만들어 보내고, htmx가 그 조각만 바꿔 끼움. JS 빌드 과정 없음.
- **왜**: 작은 팀이 복잡한 프론트엔드 빌드/프레임워크 없이 동적 UI를 빨리 만듦. 한 언어(Go)로 끝.
- **대안**: React/Vue(SPA) — 화려하고 앱 같은 UX, 대신 별도 빌드·복잡도·인력 필요.
- **트레이드오프**: htmx는 단순·빠른 개발·서버 한 곳(장점). 대신 아주 인터랙티브한 화면엔 한계(단점). **내부 관리 도구엔 htmx가 가성비 최고.**

## B-7. 암호화: AES-256-GCM (청크 방식)
- **뭐냐**: 파일을 64KB 조각(청크)으로 나눠 각각 AES-256-GCM으로 암호화.
- **왜**: GCM은 "숨김 + 변조 탐지"를 같이 함. 청크로 나누면 큰 파일도 메모리 폭발 없이 스트리밍 처리, 조각 순서 바뀜/잘림도 탐지.
- **대안(우리가 버린 것)**: AES-CTR — 빠르지만 **변조 탐지가 없음**(원래 이걸 썼다가 위험 발견하고 GCM으로 교체. `troubleshooting.md`의 실제 사건).
- **트레이드오프**: GCM은 안전(무결성 포함)하지만 약간 더 무거움(장점>단점). **데이터 무결성이 생명인 보안 제품 → 무조건 GCM.**

## B-8. 키 관리: 봉투 암호화 (Envelope Encryption)
- **뭐냐**: 파일키로 파일 암호화 → 파일키는 마스터키로 암호화해 DB 저장.
- **왜**: 마스터키 하나만 안전히 보관. 키 회전/격리 쉬움.
- **대안**: 모든 파일을 마스터키로 직접 암호화 — 단순하지만 키 교체 시 전 파일 재암호화, 격리 안 됨.
- **트레이드오프**: 봉투는 운영 유연성(장점), 구조가 한 겹 더 복잡(단점). **다수 파일·키 회전 고려 시 표준 정답.**

## B-9. 로그 무결성: DB 트리거 해시체인
- **뭐냐**: 로그가 들어오면 트리거가 자동으로 "앞 줄 지문+내용" 해시를 계산해 사슬로 엮음.
- **왜**: 누가 DB를 직접 만져 로그를 위조/삭제해도 사슬이 깨져 탐지(애플리케이션 레벨 변조 탐지).
- **대안**: 그냥 append-only 로그(추가만) — 단순하지만 위조 탐지 약함. 외부 불변 저장소 — 강력하지만 복잡/비쌈.
- **트레이드오프**: 해시체인은 추가 비용 작고 탐지력 좋음(장점). 동시 입력 경쟁 처리 필요(단점) → advisory lock으로 해결(실제 우리가 고침).

## B-10. 엔드포인트 수집: osquery + 자체 클립보드 에이전트
- **뭐냐**: 파일/USB/프로세스는 osquery(기존 오픈소스), 클립보드는 우리가 만든 작은 에이전트.
- **왜**: 바퀴 재발명 안 함 — 검증된 osquery 갖다 쓰고, osquery가 못 보는 클립보드만 직접 구현.
- **대안**: 전부 직접 개발(시간↑·버그↑) 또는 상용 EDR(비쌈·과함).
- **트레이드오프**: 조합형은 비용·신뢰성 균형(장점), 두 시스템을 합쳐 보여줘야 함(단점) → "통합 타임라인"으로 해결.

## B-11. 에이전트 실행: 윈도우 예약 작업 (서비스 대신)
- **뭐냐**: 로그인 시 사용자 세션에서 에이전트를 자동 실행하는 예약 작업.
- **왜**: 윈도우 서비스는 세션0(화면 없음)이라 **클립보드를 못 읽음**. 예약작업은 사용자 세션 → 캡처 가능. (실제로 서비스→예약작업으로 바꾼 사건)
- **대안**: 서비스(세션0, 캡처 불가), 수동 실행(꺼지면 끝).
- **트레이드오프**: 예약작업은 캡처 가능 + 자동 시작(장점), 서비스만큼의 격리·관리도구는 덜함(단점). **클립보드 캡처가 목적이면 예약작업이 정답.**

## B-12. AI: OpenAI/Gemini "tool-use" (RAG 대신)
- **뭐냐**: AI에 "조회/생성/배정" 같은 툴을 주고, 자연어 지시를 그 툴 호출로 실행.
- **왜**: 데이터가 정형(DB)이라 문서검색(RAG)보다 SQL 툴이 맞음 → 답이 실제 행에 근거(할루시↓). 변경은 사람 확인 후 + 롤백.
- **대안**: RAG(문서 Q&A엔 좋지만 정형 데이터엔 부적합), 파인튜닝(비싸고 느림·과함).
- **트레이드오프**: tool-use는 정확·실시간·행동 가능(장점), 툴/권한 설계와 인젝션 방어가 필요(단점) → 확인 게이트로 해결.

## B-13. 배포: Docker Compose + 공유 박스 + Caddy
- **뭐냐**: 서버·DB를 컨테이너로, 한 클라우드 박스에 다른 프로젝트와 공존, Caddy가 자동 HTTPS.
- **왜**: 비용 절감(박스 하나 공유) + 배포 단순 + 인증서 자동.
- **대안**: 서버마다 직접 설치(재현성↓), 쿠버네티스(강력하지만 1인 운영엔 과대), Nginx(수동 인증서).
- **트레이드오프**: Compose+Caddy는 단순·저비용(장점), 고가용성/대규모엔 한계(단점). **소규모/솔로 운영엔 이게 정답.** (확장하면 그때 k8s 검토.)
